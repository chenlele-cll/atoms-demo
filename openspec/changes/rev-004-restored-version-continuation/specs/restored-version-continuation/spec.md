# Spec Delta

## Purpose

让用户在明确恢复并确认服务端当前版本后继续提出需求，生成只基于该版本的代码与相关血缘历史，避免被离开的未来分支污染，同时保留旧版本、对话、请求幂等及候选明确采用的完整边界。

## ADDED Requirements

### Requirement: 恢复确认后明确提交当前基线

系统 SHALL 仅在恢复结果及服务端当前版本已确认后允许用户明确提交新生成，复用 `POST /api/projects/:projectId/generations` 和 `{requestId,baseVersionId,prompt}`。新请求 MUST 使用已确认的服务端 currentVersionId；恢复成功、预览完成、挂载或刷新本身不得触发生成。

#### Scenario: 恢复后提交新需求

- **WHEN** 用户确认恢复到 R，查询确认 R 仍为服务端当前版本，再明确提交需求 P
- **THEN** 原生成接口接收新的 requestId、baseVersionId=R 和 P，恢复及确认期间模型请求数为零

#### Scenario: 恢复结果未知或当前已变化

- **WHEN** 恢复响应丢失尚未查明，或提交前另一标签页已改变当前版本
- **THEN** 未确认时禁止新生成；过期请求被拒绝，保留需求并重新读取当前信息，不自动换基线提交

### Requirement: 模型历史仅反映冻结基线血缘

生成历史 MUST 只包含冻结基线自身及递归 parent 链内生成版本所关联的同项目 succeeded run 的 user/assistant 消息，且 run.resultVersionId 对应链内版本、run.baseVersionId 对应该版本 parent。其他分支、无关联消息、failed/cancelled/interrupted/running 及无关未采用候选历史 SHALL 不进入模型上下文；不得依赖提示词警告代替筛选。

#### Scenario: 从未来分支恢复后续写

- **WHEN** 版本链 T→A→B 已存在，另有 A 的未采用兄弟候选 C、失败与取消消息，用户恢复 A 后生成
- **THEN** 模型可收到生成 A 的成功历史，不能收到 B、C、失败、取消、未关联或其他项目的需求与摘要；所有原记录仍可通过持久历史读取

#### Scenario: 恢复模板基线

- **WHEN** 用户恢复到模板 T 并提交新需求，项目仍存有多条生成历史
- **THEN** 模型历史为空，只使用 T 的身份元数据、固定规则和本轮需求，代码由 T 的冻结文件工具提供

#### Scenario: 恢复此前未采用的成功版本

- **WHEN** 一个关联成功 run 的历史生成版本被明确恢复为当前，再作为新请求基线
- **THEN** 该版本自身及祖先的合法成功历史可进入上下文，不要求持久化“曾采用”标记；它的无关兄弟和后代仍被排除

### Requirement: 历史预算与当前需求保持明确

系统 SHALL 在血缘筛选后先取 sequence 最大的至多 10 条消息，再按从近到远保留正文累计不超过 16 KiB 的整条消息，最后按 sequence 升序发送。当前 prompt MUST 仅作为本轮新需求加入一次，不从新受理消息重复读入；既有 256 KiB 累计上下文和完整工具结果限制保持。省略数反映受理前项目历史总数减实际选入数，不删除消息。

#### Scenario: 无关消息不能挤掉相关历史

- **WHEN** 项目最新超过 10 条消息均属于被离开的分支，而更早消息属于当前基线链
- **THEN** 先筛选血缘再选最近 10 条，相关历史可被选入；字节不足时整条跳过，不从第 11 条补位，顺序仍为持久序号升序

#### Scenario: 多字节预算和新需求一次

- **WHEN** 合法血缘历史含中文正文且接近 16 KiB，新生成被受理
- **THEN** 按 UTF-8 字节计算保留完整消息，首个实际模型请求中本轮新需求只有一个新增消息位置，省略统计不包括新受理的 user 消息

### Requirement: 工具和候选基于恢复的不可变代码

生成工具 SHALL 读取本轮受理时冻结的恢复版本完整文件，不从模板目录、旧最新版本或页面缓存替换代码。新候选 MUST 以恢复版本为 parentVersionId，sequence 为项目所有已存版本最大值加一；保留旧快照和消息，保存成功保持 previewStatus=unverified 且不修改 currentVersionId，之后仅经明确 adopt 切换。

#### Scenario: 恢复后产生新分支候选

- **WHEN** T→A→B 已存，当前恢复为 A，工具读取 A 的独特源码并提交新候选 D
- **THEN** 实际后续模型请求含 A 的读取正文而不含 B 的替代代码，D.parentVersionId=A 且序号大于所有旧版本；保存后 current 仍为 A，旧 T/A/B 和原消息不变

#### Scenario: 候选预览后明确采用

- **WHEN** D 保存后用户通过既有候选检查完成本轮预览并明确 adopt，预期当前仍为 A
- **THEN** 使用既有采用契约确认 D 为当前，生成 succeeded 或预览完成本身不自动切换，不产生可信验证或曾采用历史标记

### Requirement: 恢复与生成竞争拒绝基线替换

恢复、新生成和候选采用 SHALL 共用项目活动与持久 running 的准入边界；活动项目拒绝冲突操作，无执行者 running 返回未确认。新生成在受理及候选提交时 MUST 检查 currentVersionId 仍等于请求基线，发生变化拒绝并保留已确认状态，不合并、不静默重设基线。网络等待不得持有数据库写事务。

#### Scenario: 恢复和生成竞争

- **WHEN** 恢复与新生成接近同时执行
- **THEN** 恢复先提交则旧基线的新生成被拒绝；生成先受理则恢复返回 busy，孤立 running 返回 unconfirmed；不产生基于未确认版本的新候选

#### Scenario: 执行期间基线异常改变或提交失败

- **WHEN** 已受理生成期间基线被改变，或候选、摘要、成功状态的写入发生故障
- **THEN** 不保存部分候选或成功摘要，不回写 current；保留已受理输入，终态无法落盘时明确未确认，不以新请求掩盖故障

### Requirement: 原请求重放与费用边界保持

系统 MUST 在会话归属校验后优先处理原 requestId 的同载荷重放，即使当前已恢复到其他版本也返回原 run/候选且不再调用模型或追加消息。同 ID 不同基线或需求 SHALL 返回 REQUEST_CONFLICT；已知失败的新尝试需用户明确新 ID，未知结果仅查询原请求，不自动重试或重新计费，未知用量保持 null。

#### Scenario: 恢复后重放未来分支原请求

- **WHEN** B 的原生成请求已成功，当前恢复为 A 后重放 B 的完全相同请求
- **THEN** 返回原 B run/候选，不把它变成基于 A 的生成，也不更改 current、重复计费或增加记录

#### Scenario: 断流未知与已知失败重试

- **WHEN** 续写流中断或终态未确认，随后用户查询；或原 run 已确认失败后明确重新生成
- **THEN** 前者只查询原 requestId 且无新模型请求；后者使用新 requestId 与重新确认的当前基线，仍受原预算、配额和零自动重试约束

### Requirement: 分层验收区分受控请求和真实全链路

内核验收 SHALL 使用实际 SDK 的受控请求与真实临时 SQLite，验证历史内容、工具读取、分支保存、失败、重放与重开，不依赖完整工作台。完整 HTTP/UI 验收等待相关能力实现，REV-005 MUST 负责真实模型、真实预览交互、恢复续写采用与重开；fixture 或结构校验不得冒充真实全链路通过。

#### Scenario: 无工作台先验证内核

- **WHEN** GEN-004 内核可用而 GEN-007 尚未实现
- **THEN** 可通过同一内部生成入口捕获实际 SDK 请求并检查临时数据库结果，报告 fixture，不伪造公开 API 或 UI

#### Scenario: 完整真实验收交接

- **WHEN** GEN-005/006/007 与 REV-002/003 实现后进入 REV-005
- **THEN** 真实用户操作恢复、明确续写、读取恢复代码、预览与明确采用后重开，分别记录模型、浏览器、持久化结果及未知费用，不自动补跑失败的计费操作
