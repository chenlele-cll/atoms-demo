# Design

## Context

范围见 [proposal.md](./proposal.md)。部署身份和数据规则由 [Lifecycle](../../../docs/engineering/lifecycle.md#deployment-release-identity) 维护；DEP-002 的隔离框架测试不证明真实部署通过。DEP-003 只有提案与前提记录，发布构建、apply 及目标环境基线均尚不可用。

用户已明确本次先实现部署脚本框架，依赖允许留待接入；DEP-003 的离线框架可以继续，DEP-004 的真实验收仍等待发布与执行接点。本设计保留为后续目标验收依据，本次不提前构建、连接服务器或执行故障场景。

## Goals / Non-Goals

**Goals:** 将原有部署规则转成可观察、可复核的目标验收，前提不满足时明确记录阻塞。

**Non-Goals:** 不在验收任务中补写发布器、修改发布包格式或产品能力；不将入口拒绝执行当作部署幂等性，不对未知服务注入故障。

## Decisions

### Evidence gate

先核对真实发布构建入口、至少一个完整且匹配目标平台的产物、DEP-003 实际部署实现和目标环境的成功基线。缺任一前提即停止有状态场景；基线未知不等于未部署。上游依赖仍分别由既有任务维护。

只复现当前未实现入口的失败保护，不读取真实 inventory 或发起 SSH；对仍匹配源码的 DEP-002 框架证据直接复用。DEP-003 的连接失败记录保留原时间与来源，不冒充本任务的新连接结果。

### Acceptance matrix

每行在 DEP-003 实现后使用其最终命令；目前不虚构未实现的 release/config/rollback 参数。先准备归属明确的专用验收实例、测试项目和持久库、真实发布包 A 及已通过的冷备份，执行重复发布场景；B 在代码更新阶段实际构建并验收，随后用于回退/故障场景。不能把损坏配置、故障包或 SIGKILL 注入现有用户实例。

| 场景 | 操作 | 必须观察的结果 |
| --- | --- | --- |
| 相同包/配置重复发布 | 健康 A 连续部署两次 | releaseId/current/配置指纹不变，无新增包、切换或服务重启；比较服务启动时间及 PID 身份、实际健康与 API |
| 同包停止后恢复 | 停止所属验收后端，再部署 A | 使用 A 原 ID，恢复单实例且真实健康；不能因 ID 相同跳过健康检查 |
| 真实代码更新 | 在隔离源副本改一个可观察构建输入，构建并验收 B，再更新 | 输入与内容变化，选择 B；没有匹配包才新建 UUID；旧包完整保留，页面/API 显示实际变化，原项目仍能重开 |
| 运行配置单独更新 | 同一包更改一项允许的运行配置，随后再次部署 | 包 ID/内容不变，私有配置指纹变化；仅受影响服务一次重启/reload；第三次无变化执行不再重启，原有秘密配置保留 |
| 坏包/错误平台 | 使用隔离副本篡改清单或内容、制造越界链接/平台不匹配 | 激活及服务停止前非零拒绝；当前成功记录、服务、数据及其他站点不变 |
| 配置校验或上线健康失败 | 在专用验收实例使用坏新配置/包 | 非零且不记录新成功版本；保留旧包与失败证据，兼容旧包可恢复并通过真实健康，数据不被旧备份覆盖 |
| 兼容与不兼容回退 | 使用已保留兼容 A，再对隔离库验证高 schema/不兼容旧包 | 兼容回退沿用旧 UUID；不兼容回退被明确拒绝，不自动降级或恢复旧库；只对测试库操作 |
| 并发与中断 | 对同一验收目标并发发布，在上传/切换阶段分别中断 | 按 DEP-003 互斥契约串行或明确失败；无部分成功记录、孤儿服务或同库双实例；恢复后只用完整包，无关进程/站点继续可用 |
| 持久数据与代理 | 在专用项目保存数据，更新/停启/回退后重开并访问最终地址 | 同一会话/项目/当前快照及内容摘要一致；冷备份 quick_check 可用；静态深链接、API、TLS 与流传输逐项有真实结果 |

运行配置的比较与必要环境快照只保存在权限受限的私有证据目录。PID 变化需结合启动身份与监督器状态，不单凭进程号判断重启；SQLite 内容以测试项目的逻辑快照比较，运行库不复制单个 sqlite 文件，也不通过文件摘要判断逻辑数据一致。

### Reporting

每个场景记录源于真实目标、隔离 fixture 或未执行，关联实际 releaseId/内容指纹、配置指纹、目标平台/工具版本、命令、时间、退出码和前后状态；任何缺项不标 passed。公开工件仅放脱敏摘要；秘密、cookie、数据库和原始日志保存在忽略的 test-results/dep-004/。

不引入新测试框架，待部署契约存在后复用项目现有 Node/Ansible/浏览器与生产入口完成场景。普通 check/verify/CI 不连接服务器、改配置或执行计费模型。工程结构校验通过不等于目标验收通过。

## Risks / Trade-offs

- 发布/连接前提缺失 → 当前只完成检查和矩阵，实际验收任务保持未完成。
- 验收过程中服务归属或库来源不明确 → 停止场景，不按端口杀进程、不操作其他站点。
- schema 变化使旧应用不可读 → 保留当前库与备份，不通过恢复旧库伪装代码回退成功。
- 流式/预览依赖实际网络 → 在最终访问环境单独验证，不能用模板渲染或定时器充当通过。

## Migration Plan

本步没有目标迁移。GEN-009 产物和 DEP-003 可执行流程就绪后，从前提门禁重新开始，确认专用验收实例与冷备份，再顺序执行更新/故障场景；结束时保留用户选择的有效版本和持久数据，只清理本次已确认的临时资源。
