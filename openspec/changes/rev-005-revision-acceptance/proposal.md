# Proposal

## Why

Top 2 的历史查询、恢复与恢复后续改需要共同证明：恢复的是已存快照，后续生成基于服务端当前版本，旧分支既被保留又不会误入上下文。REV-005 将 REV-001～004 的这些保证落实为无凭据自动化和显式真实模型专项，避免把候选保存、编译成功或本地回归当成业务与线上验收通过。

## What Changes

- 规划未来新增 `pnpm smoke:revision` 与独立 `pnpm smoke:revision:live --live`，前者使用测试构造注入的受控模型传输、真实临时 SQLite、系统 Chrome/playwright-core 与真实 Sandpack；后者复用已确认的服务端模型配置及正常工作台。两个命令目前均不存在，本轮不实现或执行。
- 固定同项目 V1 报价 → V2 加急并采用 → 历史预览 V1 → 明确恢复 V1 → 刷新/后端重启 → V3 追加需求的验收序列。分别检查 current、parent、全项目最大 sequence、快照内容哈希、旧 V2 保留与各阶段模型请求增量。
- 验证历史倒序分页元数据与完整快照读取分离；恢复只原子切换 current，不生成代码、不删除历史，template 与有效 succeeded 生成快照可恢复，CAS、busy、unknown 等状态按所属 REV 契约处理。
- 覆盖失败、取消、未确认、并发竞争、响应丢失、跨会话、320/375px 窄屏和键盘操作；复用 GEN-006 预览与 GEN-007 工作台，保留原导航、案例筛选和报价交互。
- 规划所属资源清理、端口保护、信号中断和隔离证据；默认 check/verify/CI 不调用真实模型，也不触发修复、付费重试或能力探针。
- 当前已实现模板隔离预览、项目持久化 API 和内部有界生成，已有一次真实 quote 候选保存但预览未验证；公开生成、采用、工作台及 REV 能力仍是实施前置。GEN-008/009/010 是相邻规划，不能将其旧现状描述或工件齐备视为运行通过。

## Capabilities

### New Capabilities

- `revision-acceptance`：描述 REV-001～004 既有产品保证在历史查询、恢复、续改与失败路径中的验收可观察保障，以及 fixture/live 证据成立的条件。这是对应保证的验收落实，不是新生产接口或额外产品功能需求。

### Modified Capabilities

无。现有长期规格清单为空；本变更不重定义其他 REV 的 HTTP、状态或上下文规则，不改变 GEN 的生成、预览与采用契约。

## Impact

- 未来实施涉及具体浏览器场景、SDK fixture、runner 控制测试及根命令对接，沿用 Node 测试器和已有依赖，不增加测试框架或生产假模型配置。
- 验收消费 REV-001 历史列表、REV-002 恢复、REV-003 历史 UI、REV-004 当前基线与 parent 链上下文；协议缺口由对应任务解决，验收不得自行扩展生产 API。
- GEN-008 的隔离、摘要和串行编排按实际可用程度复用；GEN-010 的显式 live 与安全调用事实按需复用，不替代其 Top 1 双需求验收。GEN-009 的独立产物、反代、部署和最终环境范围完整保留。
- 本次独占 `openspec/changes/rev-005-revision-acceptance/`，只生成规划工件，所有局部任务保持未勾选。不实现脚本/代码、不 apply、不提交，不编辑其他文件；仅规划 REV-001～005，不规划 Top 3 分享、Diff、复杂分支或自动修复。
