# Spec Delta

## Purpose

将 REV-001～004 的历史查询、历史预览、原子恢复和恢复后续改保证落实为可观察的验收标准，证明已保存内容与当前选择一致、旧历史保留且其他分支不会误入后续需求。该能力仅约束对应保证的验收证据与结论，不引入新的生产接口或产品功能。

## ADDED Requirements

### Requirement: 历史查询证据反映真实版本元数据

历史验收 SHALL 检查 REV-001 的倒序分页结果、current/parent、需求摘录、摘要和 changedFiles 与已存版本关联一致，列表不包含代码；完整内容仅通过既有版本读取取得。查询与历史预览 MUST 不产生模型请求或改变 current。

#### Scenario: 分页期间当前选择已经恢复

- **WHEN** 项目已保存 V1、V2，当前恢复为 V1，所有者以 limit 和 beforeSequence 分页查询历史
- **THEN** 结果仍按 sequence 倒序且跨页不重不漏，V2 保留，current 标识指向 V1，parent 与对应需求/摘要/changedFiles 可核对，列表不含快照代码，查询前后模型请求计数不变

### Requirement: 恢复证据证明只切换已存当前引用

恢复验收 SHALL 证明 REV-002 对 template 或有效 succeeded 生成快照的恢复仅原子切换 current，所有版本内容哈希和历史记录保持不变，不新建版本或调用模型。生成成功候选 MUST 与已采用当前版本分别记录，预览不能冒充恢复确认。

#### Scenario: 先预览再恢复 V1

- **WHEN** V2 已采用，用户历史预览 V1 后取消确认，再次打开并明确确认恢复 V1
- **THEN** 取消时 current 仍为 V2且无恢复请求；确认后服务端 current 为原 V1，V1/V2 内容哈希及历史数量不变，恢复与查询模型请求增量均为零

#### Scenario: 恢复模板或无有效成功结果的目标

- **WHEN** 所有者分别尝试恢复已存模板快照和不满足有效 succeeded 关联的生成目标
- **THEN** 模板可按既有条件恢复；无效目标被拒且 current/历史不变，不以失败、取消或未确认记录伪造可恢复成果

### Requirement: 恢复失败与不确定结果保留真实选择

验收 SHALL 观察 CAS 冲突、busy、unknown、存储失败与响应丢失时的真实持久结果。活动或未确认生成期间不得错误切换 current；确认响应丢失后 MUST 通过查询确认，查询不可用时保留待确认状态，不自动重发恢复或生成。

#### Scenario: 同一预期版本发生竞争

- **WHEN** 两标签页以同一 expectedCurrentVersionId 向不同合法目标恢复
- **THEN** 至多一次 current 切换成功，另一方观察到冲突并刷新真实选择；没有覆盖竞争胜者、额外版本或模型请求

#### Scenario: 已提交但恢复响应丢失

- **WHEN** 服务端已恢复 V1，但客户端未收到有效响应且首次确认查询失败
- **THEN** 界面先保持待确认；后续只读查询恢复服务后可确认实际 current，不能因网络错误显示已失败回滚或自动再次恢复

#### Scenario: 生成运行中或持久化失败

- **WHEN** 有活动/未确认生成，或恢复事务发生受控写入失败
- **THEN** 分别观察到对应拒绝/待确认处理或事务回滚，当前选择不被虚假成功覆盖，已有快照和需求保留

### Requirement: 恢复后的新需求使用当前分支

续改验收 SHALL 证明 REV-004 从服务端 current 读取代码与 parent 链相关上下文，排除其他分支需求；新快照 sequence 使用项目全局最大值加一，旧历史保留。编译、业务操作和显式采用 MUST 分别取得证据。

#### Scenario: 恢复 V1 后生成 V3

- **WHEN** V1 实现报价和案例筛选、V2 增加加急并已采用，恢复 V1 且刷新/重启后用户明确提交不含加急的 V3 需求
- **THEN** 新 run 基线和 V3 parent 均为 V1，V3 sequence 为原项目最大 sequence 加一；上下文不含 V2 加急分支需求，V3 无加急功能误复活；V2 原内容仍可读取，V3 采用前 current 仍为 V1

#### Scenario: 页面缓存基线过期

- **WHEN** 另一标签页已改变 current，旧页面尝试继续修改
- **THEN** 按既有冲突流程更新服务端基线，不静默以旧候选或历史预览作为基线，不自动追加付费重试

### Requirement: 重开后的业务与访问行为可核对

验收 SHALL 在同一作者会话和数据库下检查刷新、后端重启后的版本标识与内容哈希，并实际操作报价、案例筛选和原导航。桌面、320/375px 和键盘流程均需可用，跨会话查询、读取与恢复 MUST 保持既有访问隔离。

#### Scenario: 恢复后的持久选择与交互

- **WHEN** 已恢复 V1，刷新页面并停止再启动所属后端，随后从同一会话打开项目
- **THEN** current 仍为 V1且内容哈希一致，真实预览重新编译后报价/筛选/导航可操作，临时输入可重置且有说明；重开没有新模型请求

#### Scenario: 窄屏键盘及另一会话

- **WHEN** 作者在窄屏或仅用键盘选择历史、预览、取消/确认恢复，另一会话访问相同项目/版本并尝试恢复
- **THEN** 作者操作、焦点和错误反馈可达且宿主无横向溢出；另一会话无权读取或恢复，与不存在资源保持既有响应语义且不泄露代码/需求

### Requirement: fixture 与真实模型验收结论分离

验收结果 SHALL 区分 fixture、live、not-run 及生成、保存、编译、业务、采用、重开各阶段。真实模型专项 MUST 仅经显式入口和正常工作台逐项触发新需求，复用现有模型配置，无自动修复、重试或默认 check/verify/CI 真实调用；编译成功不能单独构成业务成功。

#### Scenario: 无凭据自动化与显式真实验收

- **WHEN** 分别执行无凭据回归和显式真实模型专项
- **THEN** 前者通过受控传输驱动真实持久化与预览且标为 fixture；后者的 V1/V2/V3 各由一次明确用户提交驱动并有实际调用计数，失败即停止后续新需求，不把 fixture 或旧候选作为本次真实成果

### Requirement: 验收资源与证据仅属于本次运行

验收 SHALL 将资源和证据关联到本次输入、构建与 runId，端口冲突不停止占用者，SIGINT/SIGTERM 后停止新场景并有界清理所属资源。缺前置、空/旧证据、未完成用例或清理失败 MUST 不报告整体通过；本地与线上结论分别记录。

#### Scenario: 冲突或中断

- **WHEN** 未知服务占用端口，或本次浏览器运行中收到 SIGINT/SIGTERM
- **THEN** 占用者保持可用；中断后不触发新需求，仅关闭本次浏览器/进程和所属临时资源，报告真实取消/清理结果并非零退出

#### Scenario: 本地证据已完成但线上未运行

- **WHEN** 本地 fixture 或 live 验收通过而最终服务器尚未验收
- **THEN** 报告仅确认对应本地范围，线上仍为未验证，GEN-009 部署范围及 Top 3 未运行状态不被替代
