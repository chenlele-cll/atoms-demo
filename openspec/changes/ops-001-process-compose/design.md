# Context

用户指定执行 `OPS-001`。前后端已有独立命令、固定开发端口和健康接口。使用官方 Process Compose 原生配置管理进程，避免自建守护、重试及日志系统。

# Goals / Non-Goals

- 目标：配置真实开发进程、就绪探针、有限重试、停止信号及日志；固定工具版本，实测成功和失败。
- 非目标：manager、自动 bootstrap、完整 doctor、容器、数据库、生产编排或 UI 变更。

# Decisions

- 官方发布版本固定为 `.process-compose-version` 中的 `1.122.0`；二进制校验官方 SHA-256 后保存在忽略的 `.tools/process-compose/1.122.0/`，不修改全局工具。自动安装在后续 bootstrap 实现。
- 根 `process-compose.yaml` 使用官方 schema 严格解析，调用既有 `pnpm dev:backend` 与 `pnpm dev:frontend`。两服务没有启动依赖，前端不因后端未就绪而被阻塞。
- 托管开发 profile 固定回环地址和 3001/5173 端口，固定前端代理到该后端；不注入根 `.env`，应用继续读取自身配置，独立启动方式保持原行为。
- 每个服务启动前以 Node 原生 socket 尝试绑定自己的端口。该检查只检测冲突并退出，不终止其他程序；不实现持久锁或原子端口接管。检查与服务实际绑定之间仍有竞争窗口，后续 manager 需结合归属和有界等待判断状态。
- HTTP readiness 每次有超时；`on_failure` 最多重试两次并有退避，保留可诊断状态。实测探针持续失败触发两次重试后，最后一轮仍可能保持 `Running / Not Ready`；使用非零就绪结果及显式停止诊断和清理，不能承诺原生配置自动终止所有未就绪进程。运行中的 supervisor 或一次 CLI 成功不代表全项目健康。manager 的全局截止时间与收敛另行实施。
- 使用进程组 SIGTERM 和十秒停止期限；日志放在忽略的 `.runtime/process-compose/`，使用原生日志轮转。手动控制只连接本仓库的 Unix socket，禁用额外 TCP 控制端口。
- 原生 `up` / `down` 与未来幂等 manager 区分；本步不宣称重复启动或停止已实现幂等。

# Risks / Trade-offs

- 本步需要按文档选择正确 Node/pnpm 并手动准备固定版本工具和运行目录。macOS arm64 实测不等于其他平台已验证。
- HTTP 200 只表示探针条件满足；验收另外检查健康响应结构和前端 API 代理。没有产品生成或持久化能力。
- 本地日志可能包含页面和应用数据，遵循既有日志规范并保持忽略。日志轮转配置不等于已做容量压力测试。

# Migration Plan

先固定工具和配置，再验证原生解析、双服务和单服务启动、故障与清理；更新可用命令及未实现范围。回退只移除本变更新增配置、脚本和导航，不处理其他未提交任务。
